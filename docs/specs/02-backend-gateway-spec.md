# 02 — Backend Gateway Spec (FastAPI: Auth, Onboarding, Approvals, Chat, SSE)

## 1. Introduction and Overview
### Purpose and Audience
Defines the FastAPI gateway — the only public ingress. No agent logic here. Audience: backend engineers, security reviewer.
### Project Scope and Exclusions
In scope: auth/RBAC, validation, rate limits, §7 REST + SSE fan-out, Arq enqueue, audit writes. Excludes: CrewAI logic (04), retrieval internals (03), deterministic executor side-effect code co-located but invoked post-approval (05 calls via MCP).
### Definitions, Acronyms, and Abbreviations
RBAC roles: `employee/hr_admin/service`. SSE channel `trace:{session_id}` = Redis pub/sub per agent run.
### References and Supporting Material
Plan §§2,3,5,7,10; 00-overview; 01 (DB/Redis); FastAPI + Arq docs.

## 2. General System Description
### Product Perspective and Context
Stateless gateway between Next.js/n8n and Postgres/Redis/RAG/worker. Contains no LLM prompts.
### System Functions (High-Level)
Authenticate → authorize → validate → persist state → enqueue jobs → stream traces → log audit.
### User Classes and Characteristics
`service` (machine key, trigger only), `hr_admin` (pipeline/HITL), `employee` (own roadmap/chat).
### Design and Implementation Constraints
Pydantic v2 everywhere; row-level scoping (`employee` queries force `employee_id = token.sub`); server-side region/dept resolution for chat (never trust client).
### Assumptions and Dependencies
OIDC issuer URL configured; Arq worker online; Redis available for SSE fan-out.

## 3. Functional Requirements
- **F-API-1 Trigger:** `POST /api/v1/onboarding/trigger` (role `service`, `Idempotency-Key` required) → 201 case (`pending_ingestion`) + enqueue plan job; duplicate key → 200 existing case.
- **F-API-2 Pipeline:** `GET /api/v1/cases?status=` (hr_admin); paginated.
- **F-API-3 Stream:** `GET /api/v1/cases/{id}/stream` (hr_admin, SSE `text/event-stream`, heartbeat 15 s, replay last N from audit on reconnect).
- **F-API-4 Plan:** `GET/PUT /api/v1/cases/{id}/plan` (hr_admin); PUT creates new version + diff, sets `current_plan_version`.
- **F-API-5 Approval:** `POST /api/v1/approvals/{plan_id}` `{decision: approve|reject, comment}` → records approver/timestamp → on approve enqueues execute job.
- **F-API-6 Employee:** `GET /api/v1/me/roadmap`, `PATCH /api/v1/me/checklist/{id}` (own case only; mandatory-task guard).
- **F-API-7 Chat:** `POST /api/v1/chat` → resolve profile server-side → call RAG (03) → persist `chat_logs` → return answer + citations.
- **F-API-8 Reindex:** `POST /api/v1/admin/reindex` (hr_admin, rate-limited) → enqueue ingestion.
- Validation/errors: 400 Pydantic details; 401/403; 404; 409 idempotency conflict → existing resource; 429 rate limit; 5xx → Sentry + `audit_events` entry.

## 4. External Interface Requirements
### User Interfaces
None (headless; UI in 06 consumes these endpoints via TanStack Query + EventSource).
### Hardware Interfaces
None.
### Software and Database Interfaces
SQLAlchemy→Postgres; `redis.asyncio` pub/sub; `httpx`→RAG service; Arq enqueue (`plan_job`, `execute_job`).
### Communications and API Interfaces
REST JSON + SSE; `Authorization: Bearer <JWT>` except service key on trigger; per-role rate limits (chat 30/min/user, trigger 60/min/key, reindex 2/hr).

## 5. System Features and Capabilities
### Core Modules and Subsystems
`backend/routers/{onboarding,cases,approvals,me,chat,admin}.py`, `deps/auth.py`, `sse.py`, `jobs.py`, `audit.py`.
### User Authentication and Authorization Roles
OIDC→JWT (MVP: JWT stub behind same interface if SSO not ready); RBAC decorator per endpoint; service API key rotation.
### Reporting and Analytics Modules
Every mutation writes `audit_events`; chat writes `chat_logs`; OTel spans per request + job IDs propagated.

## 6. Non-Functional Requirements (NFRs)
- Performance: API p95 < 300 ms (excl. agent/chat); SSE first event < 2 s after job start.
- Security: JWT verify (issuer/aud/exp), RBAC deny-by-default, PII minimization in logs, secrets from Vault/env.
- Reliability: idempotent trigger; at-least-once enqueue (DB state is truth; worker dedupes by idempotency key).
- Maintainability: thin routers; no LLM code; OpenAPI autogenerated.
- Scalability: stateless replicas behind LB; Redis pub/sub fan-out per replica.

## 7. Data and System Architecture
### High-Level Architecture Diagrams
`Next.js/n8n ──JWT──► FastAPI ──┬──Postgres (cases/plans/approvals/audit) ├──Redis (enqueue + subscribe trace:{session_id}──►SSE) └──RAG service (chat/retrieve)`.
### Entity-Relationship Diagrams (ERD) and Data Models
Uses 01 tables; API owns status transitions: `pending_ingestion→agent_processing→awaiting_hr_approval→executing→active|needs_attention`.
### Data Dictionary and Storage Requirements
`Idempotency-Key` header (max 128 chars); SSE event `{ts, step, message, case_id, session_id}`; audit `metadata` includes actor, IP, job ID.
